# See DontPanic used on real repos

This directory holds artifacts generated by running DontPanic capabilities
(Plan 4 architecture map + Plan 3 strict-plan-validation + Plan 4 drift)
**from inside DontPanic** against our own checked-out repos and committing
the redacted, sanitized output here as a product demo.

No DontPanic runtime code is copied into any target repo. Each artifact is
produced by running the existing `dontpanic` CLI against a sibling checkout
via `--repo-root` / `--plans-root` / `--architecture-json` and writing the
result here. Showcase regen is an explicit operator command — never
triggered from supervisor, pre-commit, or CI.

Regenerate everything in one shot:

```bash
make showcase
# or
scripts/showcase.sh
```

Either form invokes `python -m dontpanic_orchestrate showcase regen --all`
under the hood. Additional flags pass through (e.g. `make showcase
DONTPANIC_SHOWCASE_ARGS="--json"` is not supported; use the script form
`scripts/showcase.sh --json` for that).

Per-target regen (just one repo):

```bash
python -m dontpanic_orchestrate showcase regen --target=<repo_key>
```

Schema repo. **Architecture-only in v0** — intentional, not an omission.
F001's authoritative showcase config declares
`TargetSpec(repo_key="agent-conventions", supported_artifacts={"architecture"},
has_dontpanic_plans=False, has_committed_architecture_json=False)` in
[`scripts/dontpanic_orchestrate/showcase/config.py`](../../scripts/dontpanic_orchestrate/showcase/config.py),

Reason: the agent-conventions checkout has no DontPanic-style plan dirs
(`docs/plans/<plan-id>/{plan.md, features.json}`) and no committed
`architecture.json` baseline, so strict-plan-validation and architecture
drift have nothing meaningful to report. F002 reconciles its step-text
mention of "architecture + validate-plans" against F001's
`has_dontpanic_plans=False` determination — see **D005** in
[`decisions.jsonl`](../plans/2026-05-19-005-feat-dogfood-showcase-artifacts-v0/decisions.jsonl).
When agent-conventions later adopts DontPanic-style plan dirs, flip
`has_dontpanic_plans=True` in the config and the next `make showcase`
will emit the validate-plans artifact on its own.

## Local integration — deferred

DontPanic does NOT subtree, vendor, or copy runtime code into any target
repo in v0. The showcase artifacts in this directory ARE the product
surface — `make showcase` regenerates them from sibling checkouts on the
operator's machine, and no DontPanic Python lives inside agent-conventions
/ axiom / Glam.

Local integration (committed `architecture.json` in the target repo,
target-repo CI drift checks, target-repo pre-commit hooks) is deferred
until **one** of three concrete triggers fires for a given target:

1. **Committed `architecture.json`.** A target repo's operator explicitly
   wants `docs/architecture/architecture.json` committed inside the target
   for offline / contributor consumption (e.g. so a contributor reading the
   target repo on a flight without DontPanic installed can see the map).

2. **Target-repo CI drift checks.** A target repo wants the architecture
   drift probe wired into its own CI (not DontPanic's) so PRs against the
   target fail when the map goes stale, rather than relying on a separate
   DontPanic regen.

3. **Non-DontPanic contributors.** A target repo has active contributors
   who don't run DontPanic themselves and need the map in-repo (not just
   generated from DontPanic). Until then, the showcase is the contributor
   surface.

Until at least one of these fires for a target, dogfood is showcase-only
— and that's the right default. The cost of distributed runtime
integration (subtree maintenance, version drift, per-repo CI changes)
outweighs the benefit while DontPanic is the only consumer of its own
artifacts.

If you're an operator and one of those triggers has fired for a target you
own, open a follow-on plan that promotes that single target from
showcase-only to local-integrated. Don't bulk-promote all targets at once.
