# Pace: why plans take days, what is normal, what slices change

Date: 2026-08-12
Evidence: `docs/plans/2026-08-09-002-feat-decision-brief-at-gates/audit/transcript.md`

## What the last week actually cost

Plan `2026-08-09-002` (approval copy in product terms): 9 features, started 2026-08-09 evening. By 2026-08-12, F001–F005 pass; F006–F009 (now F010) still open. Calendar: **days**.

From the transcript, not vibes:

- One implementer turn routinely reads **1–7 million input tokens** (F003 i0: 7,539,783 in).
- A clean feature volley is **10–40 minutes** of model time (implement + audit, sometimes 2–3 rounds).
- F001 was dispatched **four times** the first night. Auditor signed off; `PatchCompletenessError` then blocked on unstaged `INBOX.md` / audit JSON — the run’s own receipts.
- F005 hit `max_iterations=2`, stopped, was re-dispatched the next calendar day, then closed `signed_off_adjacent` (operator finish after a downstream gate).
- Features run **one at a time**. Human gates, dirty-tree blocks, and sleep stretch 40-minute volleys across days.

Trust is high because that process catches real misses. Progress feels slow because **most of the calendar is not the audit**. It is restarts, dirt, and a plan that is nine sequential volleys.

## What is normal

Say this out loud. Put a short version in the README.

DontPanic is slower than “ask Claude to do it.” That is the product.

| Kind of work | Honest calendar |
|---|---|
| One local slice, clean tree, one volley, no gate surprise | **same sitting** (tens of minutes) |
| One slice + auditor `needs_changes` + one human approve | **one sitting to one evening** |
| Cross-cutting plan with 5–9 sequential features, two vendors, gates | **days** |
| Same, plus completeness false-blocks and iteration-cap restarts | **days, and that part is not normal** |

Normal cost of trust:

- A second vendor reads the patch
- A human sees the outcome before merge
- Close wants proof, not a chat “done”

Not normal (waste, do not advertise as virtue):

- Million-token implementer prompts that re-read the universe
- Signoff then block because INBOX.md is dirty
- Hitting the iteration cap and starting the feature over tomorrow
- Nine features for one operator-visible capability
- Docs-only work going through a full adversarial volley

## Will slices make it faster?

**The outcome / slice / proof contract does not speed a volley by itself.** It stops you from locking a pile of overlapping features that each need their own 40-minute fight.

What actually changes pace:

| Change | Effect |
|---|---|
| One slice = one plan (or one dispatchable unit) | Calendar drops from days to a sitting when the work is small |
| Inherit parent outcome on a fix | No interview, no extra features |
| Parallel only when slices don’t share a tree | Wall-clock, not token, savings |
| Docs / README as a cheap slice | `dispatch_single_agent` or operator edit — not Claude+Codex×3 |
| Fix completeness so plan receipts aren’t “unstaged dirt” | Kills the re-dispatch loop that ate F001 |
| Cap context (gist + unfold) | Directly attacks the 7M-token turns |

If we keep writing 9-feature cross-cutting plans and calling each F a “slice,” nothing gets faster. Slices only help if they **bound the work we are willing to volley**.

## How to communicate it

README, one short block, near “Why not just Claude Code”:

> This is slower than one-shot coding. A single slice is usually a sitting. A plan that needs several rival reviews and a human gate takes longer — often more than one day. That wait is the review. If a *single* slice spills into a second day because the run tripped on its own receipts or burned millions of tokens rereading the repo, that is a bug in the harness, not the price of trust.

`dontpanic next` / DecisionBrief should say **expected shape**, not just “paused”:

- `in volley` — minutes left in this round (we can estimate from last turn)
- `waiting on you` — the clock is the human
- `blocked on dirt / cap` — not normal; show the exact unblock

Do not frame multi-day mega-plans as the proud default. Frame them as “this plan has N slices; each is a sitting; serial on purpose.”
