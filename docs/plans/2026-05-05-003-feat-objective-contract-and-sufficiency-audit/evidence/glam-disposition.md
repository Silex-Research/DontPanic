## Findings the operator considers materially correct

The bar D010 sets is "≥1 materially correct integrated Creator Hub journey-coverage gap (cross-feature integration concern, not just per-feature completeness)". The following findings clear that bar:

1. **High missing_feature preview-journey-absent.** The `preview` user journey is enumerated in the contract with three states and an acceptance signal explicitly demanding "Preview uses the same render path as the public feed". Features.json has zero feature touching preview. This is a *missing journey* gap — the strongest possible integration signal because it represents an entire user-facing surface not represented at the feature level. Materially correct ✓
2. **High missing_feature edit-journey-absent.** Similar story for `edit` (post-edit, distinct from F004's profile-edit). The contract's "edit experience uses the same composer as create" is a journey-spanning constraint that no feature acceptance addresses. Materially correct ✓
3. **High integration_gap end-to-end-product-surface.** This is the canonical gap class the contract was written to surface. The completion_test demands "create → edit → preview → publish → analytics → drill-down → profile feel one cohesive product, not a collection of feature screens"; F001–F005 are decomposed strictly per-feature with no acceptance criterion exercising the cross-feature flow. Materially correct ✓ — and arguably the most load-bearing finding: this is the kind of gap that produces "everything ships green individually but the product feels broken" outcomes that D010 was strengthened to catch.
4. **Medium wiring_gap analytics-drill-down.** F003 covers tile rendering + range selector but not tap-to-drill-down. The contract calls drill-down out as journey-bridging ("tapping the post in analytics should drill into the same canonical post detail"). Without explicit wiring, drill-down won't exist and the unified-surface guarantee fails. Materially correct ✓
5. **Medium wiring_gap publish-fanout-pending-ux.** F002 acceptance focuses on success metrics (3s moderation, 60s fanout) but doesn't address the publish_succeeded_fanout_pending UX banner. The user contract requires the banner; the feature acceptance doesn't. Materially correct ✓
6. **Medium coverage_gap analytics-stale-state.** Acceptance signal "Stale-data subtext appears when last refresh > 5 minutes old" has no F003 coverage. Materially correct ✓
7. **Medium wiring_gap impression-tracker-init.** Cross-feature wiring concern: F002 publishes; F003 reads analytics; neither initializes the impression tracker. This is a sneaky kind of integration gap (data-pipeline rather than UI-flow) that's easy to miss and high-cost to debug in production. Materially correct ✓
8. **Medium coverage_gap cross-device-draft-resume.** The 30s cross-device SLO is explicit in the contract's acceptance signals + required_evidence; F001 only covers app-restart persistence. Materially correct ✓

8 of 8 findings are materially correct.
